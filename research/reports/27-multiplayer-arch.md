# Исследователь 27 — Архитектура мультиплеера

Лимиты платформ проверены веб-поиском на ноябрь 2026, ссылки в конце. Страница документации Vercel из моей сессии не открылась (домен закрыт сетевыми настройками), данные о ней взяты из результатов поиска. Прикидки помечены словом «оценка».

## 1. Выбор платформы

| Вариант | Честный расчёт на сервере и таймер | Скрытые ходы | Реконнект | Работает без интернета (LAN) | Бесплатный уровень | Насколько знают агенты (оценка) |
|---|---|---|---|---|---|---|
| **Supabase Realtime** | Своего процесса нет: нужны Edge Function и SQL-транзакция, таймер — через «ленивый дедлайн» или pg_cron | Через RLS | supabase-js переподключается сам | `supabase start` требует Docker | 200 одновременных подключений, 100 сообщений/с | высоко |
| **Firebase RTDB** | Cloud Functions только на тарифе Blaze (нужна карта) | Через security rules | встроен | эмулятор | Spark: 100 одновременных подключений, поднять нельзя | высоко |
| **PartyKit / PartyServer** | Комната = Durable Object, таймер = alarm | Свой код | partysocket переподключается сам | `wrangler dev` | Workers Free: SQLite-объекты, ~100 тыс. запросов в день | средне: путают старый API PartyKit и новый PartyServer |
| **Cloudflare Durable Objects напрямую** | То же, что PartyServer | Свой код | пишем сами | `wrangler dev` | то же | средне. При «спячке» объект теряет память, состояние нужно хранить в storage |
| **Colyseus** | `this.clock`, комнаты и матчмейкинг из коробки | Schema рассылает состояние всем. Для скрытых ходов нужна фильтрация или сообщения | `allowReconnection()` | да | Нужен свой Node-хостинг | средне: API менялся в версиях 0.15–0.17 |
| **Свой сервер: Node + Socket.IO** | Всё в памяти процесса, `setTimeout` | Свой код | Клиент переподключается сам; восстановление сессии есть с версии 4.6 | Тот же `node` на ноутбуке | Хостинг: Railway (триал $5) или Render | **максимально** |
| Vercel WebSocket Functions (бета с июня 2026) | Соединение рвётся по лимиту длительности функции (~5 мин в тесте Classmethod). Общего состояния между инстансами нет | — | — | — | — | Матч на 10 минут не выдержит |

**Решение: один сервис на Node + Socket.IO.** Он отдаёт статику клиента, держит WebSocket, `/api/ai` и `/healthz`. Хостинг — Railway или Render с платным инстансом, чтобы сервер не засыпал. Бесплатный Render засыпает после 15 минут без трафика.

Почему так:
- Агенты пишут такой код без ошибок в API.
- Ровно этот же артефакт запускается на ноутбуке для LAN-демо.
- Не нужны CORS и две деплой-цели.

Supabase оставляем для аккаунтов и рейтинга. Durable Objects — путь после хакатона: одна комната = один объект, масштаб бесплатный. Переезд дешёвый, потому что логика комнаты не зависит от транспорта (`RoomCore`, ниже).

## 2. Матч с одновременными ходами

**Главное правило: `RoomCore` — чистый TS-класс.** На вход он получает `handle(msg, playerId, now)` и `tick(now)`, наружу отдаёт сообщения и `nextWakeAt`. Socket.IO — тонкая обёртка над ним. Тот же класс работает:
- в тестах с фейковыми часами: 12 раундов меньше чем за секунду;
- в браузере (`LocalTransport`), так что клиентские агенты не ждут сервер;
- в бот-симуляторе на 1 000 матчей.

**Конечный автомат матча.**
- `LOBBY`: до 60 секунд или по кнопке Start, пустые места до 4–6 занимают боты.
- Раунд `n` = `OPEN`, затем `RESOLVE`, затем `REVEAL`:
  - `OPEN` длится 35 секунд и закрывается раньше, если сходили все люди;
  - `RESOLVE` — расчёт кодом, меньше 50 мс (оценка);
  - `REVEAL` — 8 секунд анимации на клиентах.
- После 12-го раунда — `END`.
- Обычный матч: 12 × 43 с ≈ 8,6 мин. Демо-режим: 6 раундов × 26 с ≈ 2,6 мин.

```ts
// shared/protocol.ts — контракт фиксируется на H1, дальше меняется только с согласия обоих
type C2S =
  | { t: 'join'; room: string; name: string; token?: string }   // token из localStorage
  | { t: 'start' }
  | { t: 'move'; round: number; move: Move }   // можно переотправить до дедлайна, засчитывается последний
  | { t: 'pact'; to: PlayerId; terms: PactTerms }
  | { t: 'pactReply'; id: string; accept: boolean };
type S2C =
  | { t: 'snapshot'; pub: PublicState; me: PrivateState; serverNow: number }
  | { t: 'roundOpen'; round: number; deadline: number; events: EventCard[]; forecast: EventCard[] }
  | { t: 'submitted'; playerId: PlayerId }                 // только флажок, не сам ход
  | { t: 'roundResult'; round: number; pub: PublicResult; me: PrivateResult }
  | { t: 'matchEnd'; standings: Standing[]; seed: string };
// engine/: resolveRound(state, moves, rng) — чистая функция без Date.now() и Math.random()
```

**Расчёт раунда.**
1. Срабатывает дедлайн или все люди сходили.
2. Отсутствующие ходы заменяет автопилот.
3. Ходы ботов считаются на открытии раунда.
4. Вызывается `resolveRound(state, moves, rng(seed, round))`. Ходы сортируются по `playerId`. Конфликты (две ставки на одну аренду) решает правило: побеждает большая ставка, при ничьей — жребий из seed.
5. Снимок состояния пишется в SQLite или JSON.
6. Сервер рассылает публичный результат всем, а частный — каждому лично.

**Защита от жульничества.**
- Клиент присылает только намерения. Деньги, долю рынка и банкротства считает сервер.
- Чужие ходы до вскрытия не уходят никуда; во время раунда виден только флажок «сходил».
- Каждый ход проверяется zod-схемой и границами: цена 0,5–3× базовой, расходы не больше денег плюс лимита кредита, номер раунда совпадает, дедлайн не прошёл.
- Место привязано к случайному 128-битному токену, а не к сокету.
- Не больше 10 сообщений в секунду с сокета.
- Таймер живёт на сервере. Клиент только рисует обратный отсчёт по `deadline − (serverNow − clientNow)`.
- Честность случайности (commit–reveal): на старте показываем `sha256(seed)`, в конце раскрываем `seed`. Любой может пересчитать матч по логу ходов, и этот же лог потом служит «призраком».
- В рейтинг идут только матчи, где минимум 2 живых игрока. Защита от мультиаккаунтов — после хакатона.

**Сговоры.** Сервер передаёт предложение и фиксирует согласие. Сделка ни к чему не обязывает, предать можно, но факт предательства виден обоим после вскрытия.

## 3. Боты и отключения

**Боты.** Это скриптовые политики на стороне сервера, характеры — по отчёту 28. Бот видит только публичное состояние и своё частное. Свой ход он отправляет через случайные 5–20 секунд, чтобы флажок «сходил» выглядел по-человечески. LLM в ходах ботов не участвует.

**Отключение игрока.**
- 5 секунд без heartbeat — статус «reconnecting…». Место держится до конца матча.
- Пропустил дедлайн — срабатывает автопилот: повторяется прошлый ход, но без атак и новых кредитов.
- Два пропуска подряд — место занимает бот Caretaker с пометкой AFK.
- Вернулся по токену — получает `snapshot` и управление со следующего раунда.
- Вышел сам — место переходит к боту, игроку засчитывается поражение.

**Отключение хоста** ничего не ломает: комната живёт на сервере, кнопка Start переходит к следующему человеку.

**Рестарт сервера.** При загрузке комнаты восстанавливаются из снимков, клиенты переподключаются сами и получают `snapshot`. Это надо отрепетировать: на H12 убиваем процесс посреди матча.

## 4. Конвейер новостей

**Конвейер живёт отдельно от матча и никогда не стоит в критическом пути раунда.** Это скрипт `news/`:
1. Собирает источники (отчёт 22).
2. Модель со structured outputs выбирает шаблон и параметры (отчёт 23).
3. Код проверяет границы и требует 2 источника.
4. Результат — `world/YYYY-MM-DD.json`: `worldVersion` и `events[]` с шаблоном, параметрами, заголовком и `sources[]`.

Скрипт запускается раз в сутки по cron в GitHub Actions. Сервер забирает последний валидный файл при старте и раз в час. Нет файла — берётся прошлый, нет прошлого — `world/demo.json`.

**Как события попадают в матч.**
- При создании комната фиксирует `worldVersion`, это нужно для повторов.
- По seed выбираются 3–4 события и ставятся на раунды 3, 6, 9.
- Каждое событие объявляется прогнозом за раунд до срабатывания, со ссылкой на источник.
- События одинаковы для всех игроков. Эффект считает `engine` по формуле шаблона.

**Вызовов ИИ во время матча — ноль.** Тексты новостей раунда уже лежат в файле мира. Если захотите живой ИИ-комментарий — только асинхронно, с таймаутом 3 секунды и шаблоном на случай отказа. Затраты на ИИ не растут с числом матчей.

## 6. Если в зале упадёт сеть

1. **Wi-Fi зала упал, у жюри есть мобильный интернет.** Облачный сервер работает дальше. Ноутбук докладчика подключаем к раздаче с телефона. Перед выходом на сцену прогреваем сервер через `/healthz`.
2. **Интернета нет совсем — LAN-режим.**
   - Свой Wi-Fi: дорожный роутер или точка доступа ноутбука.
   - `pnpm start:lan` поднимает тот же сервер на `0.0.0.0:3000`, QR ведёт на `http://192.168.x.x:3000`.
   - Всё лежит локально: PMTiles улицы, шрифты, `world/demo.json`, кэш ИИ-текстов. `ws://` со страницы на `http` работает.
3. **Телефоны жюри не подключаются.** Режим повтора: сервер проигрывает записанный лог ходов через тот же движок, анимация на проекторе идёт вживую.
4. **Последний рубеж** — MP4 полного матча.

## 7. ИТОГ

```text

Supabase и Firebase требуют серверных функций для честного расчёта, у Firebase Spark потолок 100 подключений, Vercel WebSocket рвёт соединение по лимиту длительности функции. 2. Раунд — конечный автомат на сервере с абсолютным дедлайном.
